分支 `exp/jev-segment-intent`。离线评测脚本 + ②' 的 App 试做（见文末）。

- `cases.py` — 手写用例（断句 30 + 难例 13，叫助手 27 + 难例 7 + 验证集 14）
- `run.py` — 调 TypeSafe Jev（`jev-latest`，`/v1/systemone`），结果写 `results.json`

## ① 断句：停顿 1.3 秒时，这一段是不是说完了

问题（noul）：`segment` 是完整的意思、可以切了吗，还是在句中停下来想词？

> ⚠️ 前提有错位：真正的断句发生在**转写之前**（按停顿切音频，再把每段送去转写），那时还没有文字。
> 这里测的是「已经有了一段文字，Jev 能不能看出它说完没有」。所以结果只适用于转写之后的环节
> （切完照常转写，Jev 判定没说完就先不粘，和下一段拼起来）；要在切音频的那一刻用上，得先拿到那段的文字
> （停顿时先快速转写一遍，或者用流式转写），Jev 本身不接收音频。

| 判定 | 准确 | 误切 | 该切没切 | Brier |
|---|---|---|---|---|
| 现状：停顿即切（SilenceSegmenter） | 14/30 | 16 | 0 | 0.533 |
| Jev，末尾无标点 | **30/30** | 0 | 0 | 0.030 |
| Jev，末尾都补「。」 | **30/30** | 0 | 0 | 0.028 |
| Jev，难例 | 11/13 | 0 | 2 | 0.091 |

- 分得很开：说完的 0.64〜0.89，句中停顿的 0.07〜0.26（「他说」0.26 最高）
- ASR 在断片末尾乱补句号也不受影响（两组几乎一样）
- 错的只有极短的应答：「对」0.32、「そうですね」0.48 → 判成没说完，会晚切
- 用法建议：当**否决权**而不是切段器 —— 停顿到了先问 Jev，p < 0.3 就再等（例如最长再等 3 秒照切）。
  误判只会让应答词晚切一点，不会把一句话劈开

## ② 这段话是不是在叫语音助手（Claude Code）

state = `{app: 前台应用, text}`；问题 noul「是不是在请助手做事，而不是要打出来的正文 / 给别人的话」。

| 判定 | 准确 | 误叫 | 漏叫 |
|---|---|---|---|
| 旧贾维斯：扫关键词 | 16/27 | 4 | 7 |
| Jev noul（choice 结果相同） | **25/27** | 2 | 0 |
| 关键词，难例 | 3/7 | 2 | 2 |
| Jev，难例 | 5/7 | 2 | 0 |

- 提到 Claude 但不是在叫它的（「我昨天用 Claude Code…」「Claude 说测试都过了」「给 Claude 的提示词写成…」）全部 < 0.5，关键词法全错
- 没有唤醒词的请求（「把刚才那段改得正式一点」「总结一下这个网页」）全部 ≥ 0.72
- **Jev 几乎不看 `app`**：Slack 里对同事说的「你帮我看一下这个 PR」0.83、「帮我看一下为什么构建失败了」0.77 都判成叫助手；
  终端里口述的 commit message 0.73、「帮我记一下，下周试试 Jev」0.53 也误叫
- 叫助手的最低分 0.72，误叫的最高分 0.83 → **单靠阈值分不开**
- 用法建议：**唤醒词 ∧ Jev ≥ 0.5**。本用例 34 条里误叫 0、带唤醒词的请求全中（漏的只是不带唤醒词的 8 条）。
  关键词法最大的问题（聊到 Claude 就误触发）被 Jev 挡掉，也不会把给同事的祈使句交给助手执行

## ②' 激进方案：Jev 先判，关键词兜底？（2026-09-26 追加）

结论：**关键词当兜底反而更差，真正有效的是把前台应用的用途告诉 Jev**。前 34 条（v1 提问）上的算法对比：

| 规则 | 准确 | 误叫 | 漏叫 |
|---|---|---|---|
| Jev ≥ 0.5 ∨ 关键词（Jev 没叫就看关键词） | 24/34 | 10 | 0 |
| Jev ≥ 0.85 直接叫，0.5–0.85 要关键词 | 32/34 | 0 | 2 |
| 关键词 ∧ Jev ≥ 0.5（上面的保守方案） | 25/34 | 0 | 9 |

- 「∨ 关键词」把聊到 Claude 的正文全叫回来了
- 0.85 这条线是贴着数据画的：同样的请求重跑 3 次，分数会漂 ±0.05，真请求 0.84 和误叫 0.82 挤在一起，守不住

**v2 提问**：state 加 `app_kind`（Slack →「chat with other people」、Terminal →「developer tool」…），并在提问里点明两类误叫（聊天应用里的「帮我…」一般是对同事说的；终端里短短一句改动描述一般是 commit message）。

| | 准确 | 误叫 | 漏叫 |
|---|---|---|---|
| v1，验证集 14 | 12/14 | 2 | 0 |
| **v2，验证集 14** | **14/14** | 0 | 0 |
| v2，全部 48 | 47/48 | 1 | 0 |

- v2 是看着 v1 的错例写的，所以另写了 14 条没见过的句子（`INTENT_FRESH`）验证。v1 在验证集上又犯了同一类错（Slack 里「能不能帮我 review 一下」0.59）；v2 全对
- 代价：v2 整体更保守，「把 node_modules 删了重新装一遍」只有 0.50，「这个页面的价格是多少」0.50
- 建议的**激进三段式**（v2 分数）：
  - ≥ 0.6：直接交给助手（留 1〜2 秒可撤销）
  - 0.4–0.6：在刘海问一句（↩ 交给助手，不理就当正文）。**这里不看关键词**，否则「给 Claude 的提示词写成…」0.54 会被叫
  - < 0.4：当正文，有唤醒词也不叫
  - 48 条：直接叫 21 条（全对）、问一句 4 条、当正文 23 条（全对）。不需要唤醒词
- 进 App 的前提：用前台应用的 bundle ID 查 `app_kind`，需要一张对照表（查不到就用 unknown）

## 延迟

p50 193ms / p90 226ms（107 次，云 API）。加在 1.3 秒停顿之后，体感可接受。
Jev 是 early access 的云 API：离线不可用、按量计费，要进 App 需要降级路径（Jev 不通 → 现状行为）。

## 局限

用例是手写的、量小、标签是一个人定的。下一步应该用真实录音的切段日志（带时间戳的转写）回放。

## App 试做：叫助手判定接进听写（2026-09-26）

减法版没有助手可叫，所以只是**影子模式**：每段转写完，与加工并行问一次 Jev（v2 提问 + `app_kind`），
写日志 `intent: p=… → call|ask|text`，判成 call / ask 时在刘海「已粘回 X」后面加一句「Jev：像在叫助手 0.83」。
**粘贴行为不变**；没 key、超时（0.8 秒）、HTTP 失败都当没问过。

- 纯逻辑：`Packages/InkfallCore/Sources/InkfallCore/Net/AssistantIntentAPI.swift`（提问逐字抄 `INTENT_Q2`、三段式、bundle ID → app_kind 表），单测 `AssistantIntentTests`
- 网络：`App/Pipeline/AssistantIntentProbe.swift`，key 同上（`TYPESAFE_API_KEY` 或 `~/.config/typesafe/api_key`）
- 自测：`Inkfall --intent-test "<文字>" [--bundle com.apple.Terminal]`
- 代价：不加工时粘贴要多等 Jev 一次（p50 约 200ms，最多 0.8 秒）
- 真机上说一阵之后，`grep intent: ` 日志就是真实录音的回放数据（上面「局限」说缺的那份）
